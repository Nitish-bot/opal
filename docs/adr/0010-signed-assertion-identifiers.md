# Use signed client-generated Assertion IDs

The public `assertionId` is the public key of a fresh random keypair generated by the client for one Assertion. `create_assertion` requires that keypair to sign alongside the asserter. The client retains the key only until creation confirms; afterward it grants no authority and may be discarded. The Assertion PDA and related accounts continue deriving from the public `assertionId`, and public integrations use that ID without constructing the PDA themselves.

**Why.** The current program accepts an arbitrary caller-supplied public key as `assertion_id` without requiring its signature. An observer can copy an ID from a pending creation transaction, land first, and occupy the derived Assertion PDA. Requiring the ID keypair's signature proves that the creator generated or controls the identifier and prevents a copier from claiming it. Random public keys also avoid collisions and preserve parallel creation without a global counter or shared mutable sequence account.

**Consequences.** The Assertion ID key is a one-time creation capability, not an owner or admin key. It cannot edit, cancel, resolve, or otherwise control the Assertion. The asserter remains the economic participant and normally pays Solana transaction and account-creation costs in addition to locking the 500 USDC Participant Bond. Opal charges no separate upfront assertion fee; the 1% Bond Fee is withheld only at settlement. An integrating application may sponsor network costs, but sponsorship is not a protocol guarantee. Clients must not discard the temporary secret until creation is confirmed; if creation fails before acceptance, they may retry with it or generate a new ID. The current `CreateAssertion` accounts and argument validation must be updated before Devnet deployment to require the Assertion ID signer.
