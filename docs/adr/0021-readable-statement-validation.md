# Enforce non-empty, single-line UTF-8 statements

An Assertion statement must be human-readable, single-line UTF-8 whose exact encoded length is between 1 and 280 bytes inclusive. It must not begin or end with Unicode whitespace and must not contain Unicode control characters, line/paragraph separators, or invisible bidirectional controls. Creating clients and the onchain `create_assertion` instruction enforce these structural rules so a custom client cannot bypass them. After validation, they preserve the submitted UTF-8 bytes exactly: no Unicode normalization, trimming, case conversion, or other text rewriting occurs. Ordinary right-to-left letters and all other Unicode scalar values outside the pinned forbidden table remain valid.

JavaScript and TypeScript creating clients reject ill-formed strings before encoding, including isolated UTF-16 surrogates. They measure the limit with `new TextEncoder().encode(statement).byteLength`, never `statement.length`, and use one unchanged validated value for byte measurement, signing preview, and Anchor transaction construction. Account readers decode the stored prefix with fatal UTF-8 handling rather than silently substituting replacement characters. These rules make browser display and Borsh serialization agree without adding Unicode normalization to the protocol.

The Preview Integration API exposes statement validation as data rather than an exception for ordinary user input. `validateStatement` returns a discriminated result containing `ok`, `utf8ByteLength`, and an `issues` array whose stable issue codes are `ILL_FORMED_UNICODE`, `EMPTY`, `TOO_LONG`, `LEADING_WHITESPACE`, `TRAILING_WHITESPACE`, `CONTROL_CHARACTER`, `LINE_OR_PARAGRAPH_SEPARATOR`, and `BIDI_CONTROL_CHARACTER`. A well-formed input reports its measured byte length and every applicable issue code, with each code appearing at most once. An ill-formed JavaScript string reports `utf8ByteLength: null` and only `ILL_FORMED_UNICODE`, because encoding it would first replace invalid code units. `createAssertion` runs this validator and refuses to request a wallet signature unless `ok` is true.

The onchain instruction enforces the same protocol acceptance rules independently; Preview validation is not a substitute for program validation. Anchor deserializes the argument as a Rust `String`, so invalid UTF-8 fails before the handler and does not require a JavaScript-specific `isWellFormed` check onchain. The handler enforces the byte-length and structural rules against that valid UTF-8 value. Stable Preview issue codes describe client-facing meaning and are not aliases for Anchor's numeric error codes.

The Devnet rules pin the following code-point table rather than delegating protocol meaning to JavaScript or Rust convenience methods:

- **Control characters, rejected anywhere:** `U+0000–U+001F` and `U+007F–U+009F`.
- **Line and paragraph separators, rejected anywhere:** `U+2028` and `U+2029`.
- **Bidirectional controls, rejected anywhere:** `U+061C`, `U+200E–U+200F`, `U+202A–U+202E`, and `U+2066–U+2069`.
- **Boundary whitespace, rejected as the first or last code point:** `U+0009–U+000D`, `U+0020`, `U+0085`, `U+00A0`, `U+1680`, `U+2000–U+200A`, `U+2028`, `U+2029`, `U+202F`, `U+205F`, `U+3000`, and the invisible byte-order-mark character `U+FEFF`.

The boundary set is the Unicode `White_Space` set used by Rust plus `U+FEFF`, which JavaScript treats as trim whitespace. The bidirectional set is Unicode's `Bidi_Control` property: invisible formatting characters that can change rendered order without changing logical byte order. Ordinary Arabic, Hebrew, and other right-to-left letters remain allowed; interfaces isolate the statement as one plain-text display unit instead of relying on author-supplied direction controls. Pinning the table makes classification independent of runtime Unicode versions and prevents a JavaScript `trim()` check from disagreeing with Rust `char::is_whitespace()`. Client and program implementations share conformance vectors covering every forbidden range, each boundary-only character at the start, middle, and end, and adjacent allowed code points. Updating the table is a protocol change; it does not happen automatically when a language runtime updates.

The program does not attempt to prove that a statement is grammatical English, factually meaningful, or well specified. Those are semantic properties that a byte validator cannot determine; creating interfaces provide guidance, and integrators judge the statement together with its Resolution Spec.

**Why.** The current program checks only the 280-byte maximum, so it accepts an empty statement, surrounding whitespace, and hidden control characters. In particular, an embedded null byte can make raw account bytes contain a suffix that null-terminated readers do not display. A minimum character count would not solve this: it would reject valid short statements while vague text or padding could satisfy it.

**Consequences.** Statement length is measured in UTF-8 bytes, not characters, because the onchain field has a 280-byte capacity. Ordinary non-ASCII names and punctuation remain valid. Short statements remain valid when they satisfy the structural rules; there is no arbitrary 20-character minimum. Accepted bytes occupy the start of the fixed field, and any unused suffix is zero-filled as storage padding. A statement that occupies all 280 bytes is valid and needs no trailing terminator. Two valid Unicode sequences can render identically while remaining byte-distinct; Opal accepts that consequence, and integrations identify Assertions by `assertionId` rather than displayed text. A signing interface must show the exact string it will submit and must not display a normalized substitute. Client-side NFC alone would be bypassable, while onchain NFC enforcement would add Unicode data and versioning to protocol consensus without solving the separate byte-count requirement. Creating clients must not use `trim()`, `\s`, or a runtime Unicode predicate as the protocol definition; such helpers are acceptable only behind tests proving they match the pinned table. The current creation instruction and its error set must be tightened before the official Devnet deployment.
