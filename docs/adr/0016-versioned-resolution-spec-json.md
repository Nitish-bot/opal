# Publish Resolution Specs as versioned, schema-validated JSON

Resolution Specs use UTF-8 JSON that validates against a published, versioned JSON Schema. Devnet uses `schemaVersion: "1"` and the source schema at [resolution-spec-v1.schema.json](../schemas/resolution-spec-v1.schema.json). The required v1 fields are:

- `schemaVersion`: exactly `"1"`;
- `definitions`: an array of explicit term/meaning pairs containing non-whitespace text with no leading or trailing whitespace, which may be empty;
- `sources`: a non-empty array ordered from highest to lowest authority, with each source declaring its name, a URL beginning with the exact lowercase `https://` prefix and containing no embedded credentials, and `next-source` or `unresolvable` behavior when unavailable;
- `conflictBehavior`: exactly `highest-priority-wins` for v1;
- `ambiguityHandling`: normative statement-specific guidance containing non-whitespace text with no leading or trailing whitespace that cannot override source ordering or protocol evidence timing;
- optional `rationale`: human-readable, non-normative context that cannot override any typed rule.

The schema rejects unknown fields, whitespace-only or boundary-padded normative strings, and exactly duplicated array items. Before ordinary JSON decoding, a duplicate-key-aware parser rejects repeated decoded object member names, so escaped and literal spellings of the same key still collide. Cross-field validation also rejects a repeated definition term after trimming and case-sensitive Unicode NFC normalization, even if the meanings differ, and a repeated source after WHATWG URL serialization with the fragment removed. The final source cannot use `next-source`; creating clients enforce that cross-field rule in addition to JSON Schema validation. Every creating-client and resolver validator must enable Draft 2020-12 URI format assertion rather than treating `format` as annotation-only. They also parse every source URL and reject a non-lowercase HTTPS scheme, an empty hostname, embedded username or password, invalid URL syntax, or a raw backslash. The onchain program stores only `resolution_spec_uri` and cannot parse or validate the uploaded JSON.

The resolver treats a valid URL as input, not proof that fetching it is safe. It sends no ambient cookies or credentials, permits only HTTPS redirects, repeats the complete URL and address check for every redirect, and rejects any destination whose resolved address is loopback, private, link-local, multicast, unspecified, or otherwise non-public. It prevents DNS rebinding by connecting through controlled egress or to a validated address, and bounds redirects, time, response bytes, decompression, and accepted content types. These network checks are application rules that JSON Schema cannot express.

Devnet caps the exact uploaded UTF-8 JSON at 16 KiB (16,384 bytes). This is an Opal application-level resource bound, not an Arweave protocol restriction, upload tier, or pricing threshold. Implementations enforce it on the raw bytes before parsing and upload, then again on the retrieved bytes before signing Assertion creation. The limit deliberately remains independent of the selected Arweave uploader or gateway.

**Why.** Source ordering, unavailability behavior, and ambiguity rules cannot be reliably validated when buried in free-form Markdown. Versioned JSON gives creating clients, integrators, and the resolver one explicit contract, while documentation and applications can render the same object into participant-friendly prose. Rejecting unknown fields prevents an asserter from adding hidden normative instructions that compete with the agreed protocol rules.

**Consequences.** Creating clients fail closed before upload and again before signing Assertion creation if the exact content exceeds 16,384 bytes, contains duplicate object keys, is not valid UTF-8 JSON, does not validate against the declared schema with format assertion enabled, or fails a documented uniqueness, cross-field, or source-URL check. The resolver repeats the same validation and network-safety checks before fetching. Existing immutable specs always retain their original version and meaning; a future schema version cannot reinterpret them. Public docs publish the JSON Schema, a rendered field reference, and complete valid and invalid examples. Insignificant JSON formatting whitespace and object-key order do not change semantics, but different uploaded bytes receive different Arweave IDs; no canonical-JSON serialization requirement is added for Devnet.
