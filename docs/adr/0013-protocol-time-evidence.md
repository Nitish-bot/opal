# Use current evidence for the Devnet MVP; defer change invalidation

A Resolution Spec is immutable after Assertion creation and time-independent in what it permits. It defines the statement's authoritative sources and their priority, key definitions, and ambiguity handling, but it cannot impose an asserter-selected evidence cutoff, freeze a source at a chosen version, exclude later corrections, or instruct the protocol to wait until a date chosen in the spec.

For the Devnet MVP, evidence timing is instead a protocol-wide rule. Each resolution action applies the unchanged spec to the latest relevant information available from its authoritative sources when that action occurs. The LLM verdict therefore reflects the information available when the resolver acts. A correction during the LLM Dispute Window can motivate escalation, and voters apply the same unchanged spec to the information available when they cast. Accepted Votes remain immutable, so a correction during the Voting Window can influence later Votes but cannot rewrite earlier positions. Once the Assertion reaches a terminal truth outcome, later corrections never reopen or mutate it; an integrator that needs a new judgment creates and references a new Assertion.

**Why.** Allowing the asserter to choose an evidence cutoff lets the spec exclude inconvenient corrections and makes otherwise identical truth claims depend on arbitrary private timing rules. Keeping the rubric fixed while the protocol supplies one timing rule makes assertions easier to compare and prevents spec authors from freezing a favorable source version. It also preserves the meaning of the permanent record: it shows the result reached through the information flow that actually occurred, rather than a record that can change when a source is corrected later.

**Consequences.** A spec that attempts to impose its own cutoff or correction exclusion is malformed and should be rejected by clients; if such a spec reaches the protocol through a bypassing client, applying it should produce `Unresolvable` rather than honoring the private limitation. Source changes can legitimately produce a different verdict at a later resolution layer or in a later Assertion. Because external sources may mutate, permanent storage of the spec alone does not guarantee historical reproduction of the exact evidence visible to every actor; any future evidence-snapshot or provenance mechanism is separate from the spec and must not mutate it. A future protocol-level `resolves_at` field, if ever added, would be a universal lifecycle mechanism rather than content inside the Resolution Spec.

**Post-MVP direction `[Vision]`.** Opal intends to replace the MVP current-information rule with Assertion invalidation when authoritative source information or rubric-relative truth materially changes between Assertion creation and terminal finalization. An invalidated Assertion would produce no truth outcome, and an integration needing a judgment would create a new Assertion. Change detection, evidence capture, terminal representation, and settlement economics remain undecided. Until those mechanisms are specified in a later ADR, the MVP rule above remains normative.
