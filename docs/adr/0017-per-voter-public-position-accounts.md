# Use one permanent public account per Vote position

Devnet represents every revealed voter position in its own permanent public `VotePositionAccount`, uniquely keyed by the Vote Round and voter wallet. The Vote Round stores only fixed-size outcome aggregates, payout inputs, total position count, publication progress, and a publication-complete marker; it never stores an unbounded vector of voter positions.

The terminal outcome and payout formula finalize without enumerating every voter. The private-to-public position mapping is then published in deterministic bounded batches. Publication may process positions in any order, cannot publish one position twice, and marks the round complete only after the number of published records equals the immutable position count frozen at finalization. Until that marker is set, the public position list is explicitly incomplete even though the Assertion can already be `Resolved`. Integrators that enumerate or audit all voters must wait for publication completion; integrations consuming only the Assertion's truth outcome do not.

Batch publication is permissionless. Any caller may submit any still-unpublished valid position or bounded group of positions. The program derives every public record from authenticated finalized state: the caller cannot select a different wallet, outcome, stake, payout, or status, and a duplicate cannot create a second record or advance publication progress twice. The caller normally pays the external transaction cost; an integrating application may sponsor it, but Opal charges no publication fee and guarantees no sponsor or caller reward. Publication eligibility does not expire, so an incomplete round remains publishable until the completion marker is reached.

Each permanent public Vote position records its Vote Round, owner wallet, selected outcome, Gross Voting Stake, exact finalized payout entitlement, and `Claimable`, `Claimed`, or `Slashed` status. It does not expose the wallet's total Private Voting Balance. A wallet's bonded position and Vote position remain separate records and entitlements even when the same wallet owns both.

The voter normally funds the SOL account-creation balance for its own permanent position, including when an asserter or disputer also chooses to Vote. An integrating application may sponsor this cost, but Opal provides no protocol-level sponsorship guarantee. This is an external Solana account-creation cost rather than an Opal fee. Any preparatory account whose Vote is never accepted does not become a permanent position record and can close only through a safe unused-setup path that returns its lamports to the original payer. Once the Vote is accepted, the record and its account-creation balance are permanent and non-recoverable.

**Why.** A Vote Round has no fixed maximum number of voters. A growable vector would give the round account an eventual size ceiling, require repeated resizing and rent funding, concentrate all publication writes on one account, and make later publication or claims depend on that shared account remaining writable. Per-position accounts distribute storage and mutations across independent records, align with one immutable Vote per wallet per round, and allow one invalid or delayed position to remain isolated from every other position.

**Consequences.** Devnet incurs one permanent public account-creation cost per accepted voter position. Requiring voter or optional integrator funding prevents an unbounded voter set from imposing an unbounded permanent-storage liability on the Opal treasury. Preparing the base-layer record may reveal that a wallet intends to participate in a Vote Round while the Voting Window is open, although its selected outcome and stake remain private until publication. Publishing the voter set is not atomic with outcome finalization, so participant and developer documentation must distinguish `RoundFinalized` from `PositionPublicationComplete`. Permissionless publication removes an Opal-operator authorization dependency but does not execute automatically or guarantee that a third party promptly pays for every batch. The current `VoteResolutionRound` has aggregate fields but no voter-position account or publication progress fields; those remain `[MVP-target]` implementation work.
