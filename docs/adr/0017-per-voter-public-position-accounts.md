# Use one permanent public account per Vote position

Devnet represents every revealed voter position in its own permanent public `VotePositionAccount`, uniquely keyed by the Vote Round and voter wallet. The Vote Round stores only fixed-size outcome aggregates, payout inputs, total position count, publication progress, and a publication-complete marker; it never stores an unbounded vector of voter positions.

The terminal outcome and payout formula finalize without enumerating every voter. Before casting, each voter creates, funds, and delegates a blank fixed-size `VotePositionAccount` PDA; after finalization the PER writes that permanent account and commit-and-undelegate restores it for deterministic bounded registration on Solana. No ER-only Ephemeral Account or event is treated as a committable position, and no second per-voter publication receipt is needed. Registration may process positions in any order, cannot count one position twice, and marks the round complete only after the number of registered records equals the immutable position count frozen at finalization. Until that marker is set, the public position list is explicitly incomplete even though the Assertion can already be `Resolved`. Integrators that enumerate or audit all voters must wait for publication completion; integrations consuming only the Assertion's truth outcome do not.

Batch publication is permissionless only if the PER/eSPL feasibility spike proves the required PDA authorities. A valid caller may submit any restored, still-unregistered position or bounded group of positions. The program validates every public record against authenticated finalized state: the caller cannot select a different wallet, outcome, stake, payout, or status, and a duplicate cannot create a second record or advance publication progress twice. If a private claim raced ahead, registration creates the record as `Claimed` only when it also validates the matching restored `ClaimReceipt`; without that receipt it may conservatively expose stale `Claimable` until later synchronization. The caller normally pays the external transaction cost; an integrating application may sponsor it, but Opal charges no publication fee and guarantees no sponsor or caller reward. Publication eligibility does not expire, so an incomplete round remains publishable until the completion marker is reached.

Each permanent public Vote position records its Vote Round, owner wallet, selected outcome, Gross Voting Stake, exact finalized payout entitlement, and `Claimable`, `Claimed`, or `Slashed` status. It does not expose the wallet's total Private Voting Balance. A wallet's bonded position and Vote position remain separate records and entitlements even when the same wallet owns both.

The PER-resident claim marker, updated atomically with the token transfer, is authoritative for double-claim prevention. The claimant funds and delegates a base-created fixed-size `ClaimReceipt` before claiming; the PER writes it atomically with the claim and commit-and-undelegate restores it. A claim made after position registration—or one whose receipt was unavailable during registration—may leave the public record temporarily at `Claimable`; synchronization can advance it idempotently to `Claimed` once the receipt is restored. This projection lag never permits another payout and never moves a terminal status backward. Claim-status synchronization is permissionless only if the feasibility spike proves its PDA authority path.

The voter normally funds the SOL account-creation balance for its own permanent position, including when an asserter or disputer also chooses to Vote. An integrating application may sponsor this cost, but Opal provides no protocol-level sponsorship guarantee. This is an external Solana account-creation cost rather than an Opal fee. Any preparatory account whose Vote is never accepted does not become a permanent position record and can close only through a safe unused-setup path that returns its lamports to the original payer. Once the Vote is accepted, the record and its account-creation balance are permanent and non-recoverable.

**Why.** A Vote Round has no fixed maximum number of voters. A growable vector would give the round account an eventual size ceiling, require repeated resizing and rent funding, concentrate all publication writes on one account, and make later publication or claims depend on that shared account remaining writable. Per-position accounts distribute storage and mutations across independent records, align with one immutable Vote per wallet per round, and allow one invalid or delayed position to remain isolated from every other position.

**Consequences.** Devnet incurs one permanent public account-creation cost per accepted voter position. Requiring voter or optional integrator funding prevents an unbounded voter set from imposing an unbounded permanent-storage liability on the Opal treasury. Preparing and delegating the base-layer record may reveal that a wallet intends to participate in a Vote Round while the Voting Window is open, although its selected outcome and stake remain private until restoration. Publishing the voter set is not atomic with outcome finalization, and synchronizing a claim is not atomic with the PER transfer, so participant and developer documentation must distinguish `RoundFinalized`, `PositionPublicationComplete`, and potentially stale public payout status. If the feasibility gate passes, permissionless publication and claim-status synchronization remove an Opal-operator authorization dependency; they still do not execute automatically or guarantee that a third party promptly pays for every transaction. The current `VoteResolutionRound` has aggregate fields but no voter-position account, publication progress fields, or claim-receipt projection; those remain `[MVP-target]` implementation work.
