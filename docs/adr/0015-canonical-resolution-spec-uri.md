# Use a canonical `ar://` Resolution Spec URI

The canonical Resolution Spec identifier is exactly `ar://<id>`, where `<id>` is a 43-character unpadded base64url Arweave L1 transaction ID or ANS-104 data-item ID. The URI is exactly 48 ASCII/UTF-8 bytes, uses the lowercase `ar` scheme, and contains no gateway host, ArNS name, query, or fragment. The Preview Integration API exposes it as `resolutionSpecUri`; the target program stores those bytes in `resolution_spec_uri: [u8; 48]` with no variable length or padding. The current `auxiliary_hash: [u8; 128]` field is misleading and is renamed and narrowed before the official Devnet deployment.

Creating clients retrieve the object by its known ID and fail closed unless Arweave signature/data-root verification proves that the served bytes match that ID. No second raw content digest is part of the protocol identifier. HTTP gateway URLs and mutable ArNS names are rejected at the boundary. See [Arweave client-side verification](https://docs.ar.io/learn/verification/client-side-verification) and the [`ar://` identifier format](https://docs.ar.io/learn/wayfinder/).

**Why.** A raw digest can verify bytes but cannot locate them. A gateway URL locates data through one provider and makes the identifier depend on that provider. An ArNS name can be retargeted, which would violate Assertion immutability. A known Arweave transaction or data-item ID supplies both permanent addressing and a cryptographic verification path, while the `ar://` scheme keeps resolution independent of any gateway.

**Consequences.** Public integrations never accept or expose a free-form `auxiliaryHash`. Both the creating client and the onchain `create_assertion` instruction require exactly the lowercase ASCII prefix `ar://` followed by 43 characters from the unpadded base64url alphabet (`A-Z`, `a-z`, `0-9`, `_`, or `-`). They reject non-canonical spelling, padded or wrong-length IDs, HTTP(S) URLs, ArNS names, and trailing components. A verified existing URI may be reused for several independent Assertions. The onchain program validates this byte shape but cannot retrieve Arweave or perform full signature/data-root verification; clients and consumers must do that offchain. The current instruction's generic maximum-length check and the account's legacy 128-byte allocation must be replaced before the official Devnet deployment. A future identifier format with a different width requires an explicit versioned account change rather than silently consuming reserved bytes.
